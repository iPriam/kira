title: Command Reference
description: Every `kira` verb, its arguments, and what it does.

Every verb that takes `[file|dir]` defaults to the package directory you are standing in. Everything after `--` goes to the program.

## `run`

```bash
kira run [file|dir] [--backend vm|llvm|hybrid] [--device host|wasm32|wasm64]
         [--sanitize address] [--release] [--emit-llvm-ir] [--quit-after 5s]
         [--timings] [--show-notes]
         [-- <args...>]
```

Reports diagnostics, then executes a clean program in this process. `--backend vm` is the default.

A wasm device does not run on this machine: it builds a module and serves it to a browser, which is what running a Kira program on the Web means.

`--quit-after` ends the process that long after the program starts. The engines run the program in this process, and a program that owns a window returns only when a person closes it, so the deadline is the process's rather than a callee's.

`run` refuses a cross `--target`: it has to start what it built.

## `build`

```bash
kira build [file|dir] [--backend vm|llvm|hybrid] [--device host|wasm32|wasm64]
           [--target arch-os-abi] [--sysroot <dir>]
           [--relocation-model pic|static] [--linkage dynamic|static]
           [--sanitize address] [--release] [--emit-llvm-ir]
           [--timings] [--show-notes] [-- <args...>]
```

Compiles to an application or library artifact under `.kira-build/`. See [Running Programs](/docs/appendix/getting-started/running-programs#where-artifacts-land) for the output shapes and [Cross Compilation](/docs/appendix/toolchains/cross-compilation) for the target flags.

`--sanitize address` instruments LLVM-native code and links AddressSanitizer from Kira's managed LLVM bundle. It applies to the whole LLVM backend and the `@Native` half of a hybrid build. VM and Web builds refuse it because they emit no native code for AddressSanitizer to instrument.

The managed bundle must include compiler-rt for the selected macOS, iOS, tvOS, visionOS, Windows, Android, or Linux target. Kira reports the exact missing bundle path and never falls back to Xcode, Command Line Tools, or a compiler on `PATH`.

## `check`

```bash
kira check [file|dir] [--device host|wasm32|wasm64] [--target arch-os-abi]
           [--timings] [--show-notes]
```

Reports diagnostics and never executes. It runs the whole frontend, which includes resolving imports, preparing native libraries, and generating autobindings.

The machine matters even though nothing is emitted: autobind generates per target and native-library rows are selected per target, so a program that checks clean for this machine can fail for another one on a library it declares no row for. `kira check --target aarch64-linux-gnu` is exactly that question.

## `test`

```bash
kira test [file|dir] [--backend vm|llvm|hybrid] [--sanitize address] [-- <args...>]
```

The same pipeline `run` drives, with one difference: the entrypoint is the generated `kiraTestMain` rather than `@Main`. A suite therefore needs no `@Main` of its own, and one that has an application entrypoint keeps it, so `kira run` on the same package still runs that.

The compiler knows neither the `Test` family nor the protocol behind that entrypoint: both are Kira source in the test package. See [Testing](/docs/foundation/testing).

## `debug`

```bash
kira debug [file|dir] [--backend vm|llvm|hybrid] [--break name[:pc]] [--batch]
           [--lldb|--lldb-dap] [--dap-continues n] [--prepare] [-- <args...>]
```

Stops a running program and shows what it is doing, on all three backends. See [Debugging](/docs/appendix/debugging).

## `profile`

```bash
kira profile record|report|annotate|script|stat|diff [...]
```

Records where a program spends its time and reads the recording back. Recordings default to `kira.profile` in the working directory. See [Profiling](/docs/appendix/profiling).

## `live`

```bash
kira live [runner] [file|dir] [--backend vm|llvm|hybrid] [--watch|--no-watch]
          [--quit-after 5s]
```

Builds the program into a `.klbundle`, serves it over a loopback socket, and runs it on a runner client. Unlike `run`, it does not execute the program in this process: the app is hosted somewhere that can outlive the compiler and take a new bundle later.

Runner ids: `desktop`, `macos`, `ios`, `ios-simulator`, `ios-device`, `tvos`, `visionos`, `windows`, `android`, `web`, `linux`. The first positional is a runner id if it names one and a path otherwise, so `kira live ios` is the iOS runner and `kira live ./ios` is a directory.

See [Live and Hot Reload](/docs/appendix/platforms/live-and-hot-reload).

## `export`

```bash
kira export <apple|macos|ios|tvos|visionos|windows|android|web|linux> [dir]
            [--profile debug|profiler|release] [--surface dom|webgpu|hybrid]
```

Generates a per-platform project: an Xcode workspace, a Visual Studio or CMake preset set, a Gradle scaffold, or a servable Web bundle. Everything lands under `exports/`. The command needs a package to build from. See [Exports](/docs/appendix/platforms/exports).

## `shader`

```bash
kira shader build [--target <name>] [--emit <name>]
```

Builds every `.ksl` file in the package for all five targets and reports what each emitted, writing the sources into `generated/shaders/`.

A build alone cannot answer that question: a target that cannot express a shader leaves empty sources plus a note rather than failing, so a shader can build clean, hand the driver an empty string, and fail at shader creation with an empty info log. This verb makes that visible.

`--emit <target>` prints one target's source instead of the summary. See [KSL Shaders](/docs/appendix/shaders).

## `ffi`

```bash
kira ffi [file|dir] [--device host|wasm32|wasm64] [--target arch-os-abi]
```

Inspects and binds native libraries, regenerating autobindings explicitly rather than as a side effect of a `check` or `build`.

## `lint`

```bash
kira lint [file|dir]
```

Reports what the package's own `linter.kira` asks about.

## `doc`

```bash
kira doc [file|dir]
```

Renders documented declarations as Markdown, reading the consecutive `///` lines above each one.

## `tokens` and `ast`

```bash
kira tokens <file>
kira ast <file>
```

Print a file's lexical tokens and its syntax tree.

## `new`

```bash
kira new [--app|--library] <dir>
```

Scaffolds a project into an empty directory: `package.kira`, `app/main.kira` (or `app/<name>.kira` for a library), and a README. The package name is the directory's name.

## `sync`, `add`, `remove`, `update`

```bash
kira sync [file|dir]
kira add <name> (--path <dir>|--version <version>|--git <url>) [dir]
kira remove <name> [dir]
kira update [file|dir]
```

`sync` resolves the package graph and writes `kira.lock`. `add` and `remove` edit `package.kira` and refresh the lockfile. `update` re-resolves the graph and re-syncs; it fetches nothing, because only path dependencies resolve. See [Libraries and Packages](/docs/appendix/cli/packages).

## `package`

```bash
kira package [file|dir] [--backend vm|llvm|hybrid] [--emit-llvm-ir]
```

The distribution-facing library build. It refuses an application by name, then delegates to the same build paths `kira build` uses, so a package cannot accidentally be published with an entrypoint in it.

## `migrate-manifest`

```bash
kira migrate-manifest [dir]
```

Parses a legacy `kira.toml`, `project.toml`, or `Kira.toml` and renders it as a `package.kira` declaration. The source TOML stays in place so migration is recoverable and a package can compare the two files before removing the old one. It refuses to overwrite an existing `package.kira`.

## `help` and `--version`

```bash
kira help [all]
kira --version
```
