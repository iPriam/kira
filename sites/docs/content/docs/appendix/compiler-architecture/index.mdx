Kira is a Rust workspace. Crates live in `crates/`, organized into layers with no upward dependencies. Each crate's `lib.rs` states its layer in its first doc line, and that line is the source of truth.

## The Shared Frontend

```text
kira-source -> kira-lexer -> kira-macros -> kira-parser -> kira-semantics -> kira-ir
```

Every backend consumes the same IR, and so does the language server. Backend selection happens in `kira-build`, above all of it, which keeps the frontend independent of the CLI, of the project layer, and of any backend's linking.

### Outside the Graph

| Crate | What it is |
| --- | --- |
| `kira-lsp` | The language-server binary, over the same frontend the compiler uses. |
| `kira-bundle-host`, `kira-desktop-runner`, `kira-app-runner` | Runners. They host a `.klbundle` and see no IR, no source file, and no backend. |
| `kira-hybrid-launcher` | The binary a standalone hybrid program is staged as. |
| `kira-export` | The per-platform project generators. |
| `kira-libffi`, `kira-syscall`, `kira-network` | Runtime capability crates beneath the seam. |
| `kira-launcher` (`kira`), `kira-knvm` (`knvm`), `kira-devflow` (`devflow`) | Standalone tools, leaves depending only on `kira-toolchain`. |
| `kira-export-consumer` | A Rust program consuming a Kira library end to end, on each of the three engines. |

## Where Kira Source Lives

Kira source ships in three places, and the difference is who loads it.

| Directory | Loaded by |
| --- | --- |
| `foundation/` | `import Foundation`, found beside the compiler, on every platform. |
| `packages/` | A dependency named *by path*, which is where anything platform-bound belongs. |
| `tests-kik/` | The harness packages. |

`packages/linux` reaches the Linux kernel through `@FFI.Syscall`, and a declaration like that is refused at compile time on a target that cannot reach it, so inside Foundation it would refuse every Windows and macOS build of every program.

## The VM Stays Portable

`kira-vm-runtime` and everything below it take no filesystem, process, thread, or dynamic-loading dependency and must compile for `wasm32-unknown-unknown`. The VM consumes bytes and reaches the world only through its host capabilities.

Native-only functionality, dynamic FFI and `dlopen`, is feature-gated and lives in `kira-hybrid-runtime` and `kira-native-bridge`.

## A Runner Consumes Bundles

The `.klbundle` is the boundary: a runner reads a manifest plus payloads, with no dependency on `kira-ir`, `kira-semantics`, or any backend. **Building a bundle needs LLVM; running one never does**, which is what lets a runner ship to a machine without it.

## The Agent-Facing Servers

`kira-mcp` and `kira-lldb-mcp` share their JSON-RPC framing through `kira-mcp-protocol`. They are split by lifetime rather than by subject: `kira-mcp` answers one compiler question per call, while a debug session outlives the call that started it, so `kira-lldb-mcp` holds the LLDB processes and the built targets its sessions are debugging.

Neither is a layer. Both sit above `kira-cli`, and `kira-lldb-mcp` builds through it. See [Debugging](/docs/appendix/debugging).
