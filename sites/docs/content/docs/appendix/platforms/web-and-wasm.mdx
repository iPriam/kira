The `web` runner id maps to **Kira Wasm**, the web runner and runtime backend. Kira Wasm is not Kira Web:

- **Foundation** provides the low-level platform APIs, including `Foundation.Web`.
- **Kira Wasm** is the runner and runtime backend for browsers.
- **Kira Web** is reserved for a future framework and does not exist yet.
- Kira UI, UI Foundation, and Kira Graphics are separate from all of them.

## Building for the Web

```bash
kira build --device wasm32 app.kira      # a wasm32-emscripten module
kira export web app.kira                 # a servable browser bundle
kira live web app.kira                   # build, serve, and open a browser
```

The Web target runs the same LLVM lowering the host does, through emscripten. `crates/kira-cli/tests/end_to_end/web.rs` builds a module and compares its output against the VM's under node, so a layout mistake shows up as a wrong value rather than hiding.

Because the exported loader is a plain emscripten module, the bundle also runs headlessly: `node exports/web/main.js` executes the app and prints its output, which is how the export is tested without a browser.

## Web Surfaces

Surfaces are typed and selected with `--surface`.

| Surface | Meaning | State |
| --- | --- | --- |
| `dom` (default) | DOM rendering | Host-surface probe, reported with `HOST_*` markers |
| `webgpu` | A graphics canvas, requiring a canvas and browser WebGPU capability | Host capability evidence only |
| `hybrid` | A browser VM/native boundary runner | Refused with a precise diagnostic until a runner exists |

`--surface webgpu` records the graphics-canvas model, the canvas requirement, and the WebGPU capability in the export's `manifest.json`.

## `Foundation.Web`

`Foundation.Web` browser APIs are FFI-backed. The generated binding surface includes DOM node handles, console logging, navigator and location access, attributes, styles, classes, stable callback registration and removal, DOM event hooks, timers, callback cleanup, and WebGPU capability detection. The generated JS glue ships in a web export as `kira-browser-ffi.generated.js`.

`Foundation.Web` itself is named in Foundation rather than shipped: the DOM bindings it needs are still being built, and a file that compiles and does nothing is worse than an import that fails.

## What Is True Today

The generated module is a real WASM module with exported probes, loaded through the emscripten loader. **Only module-load capability is asserted** in the generated host module: deeper Kira-owned runtime, app, UI, layout, and render probes stay false until a real backend path produces them.

The host browser may load WASM, provide imports, create surfaces, forward events, and report errors, but it must not pretend to be the Kira renderer.

## The Portable VM Core

Separately from the emscripten path, `kira-vm-runtime` and everything below it take no filesystem, process, thread, or dynamic-loading dependency and must compile for `wasm32-unknown-unknown`. The VM consumes bytes and reaches the world only through its host capabilities.

That is what lets a Kira library's generated Rust crate run inside a browser tab with no linker at all, and it is why a host that grants no filesystem simply refuses rather than failing to build.
