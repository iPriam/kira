Equality, ordering, hashing, and enum tags are the compiler's own **native operations** — `==`, `<` / `compare(...)`, `hash(...)`, and `code(...)` / `fromCode<E>(...)` — earned by any type whose shape carries them, with no `@Derive` at all. They were once Foundation macros; the compiler now owns them, structurally and byte-identically on every backend.

What remains as a macro is the one the compiler does not own: `Serializable`, in `foundation/app/DeriveSerde.kira`, written in pure Kira, plus the builtin `@Derive(Copy)` assertion. Both are available as `@Derive` targets in any file with its own `import Foundation`.

| Derive | Generated free function | Contract |
| --- | --- | --- |
| `Serializable` | `function serialize_<Type>(v: borrow <Type>) -> String` and `function deserialize_<Type>(s: borrow String) -> <Type>` | value to compact wire string and back, trapping on malformed input |
| `Copy` | none (compiler assertion) | opt-in assertion that a type is structurally copyable |

The generated name is glued to the derived type's exact name (`serialize_Point`,
`deserialize_Point`), and that is a fixed contract other tooling reads.

There is no `Clone` or `Lerp` derive: a value whose every leaf is `Copy` copies with a plain binding, and interpolation is a plain overload — `function lerp(from: borrow T, to: borrow T, amount: Float) -> T` written fieldwise, joining the ordinary `lerp` overload set. `Serializable` is the lone survivor because its wire form is a reflection over field, type, and variant *names* that no native operation carries.

## The Native Operations

Equality, ordering, hashing, and tags need no derive: the operator (or operation) and the generic bound read the same structural fact off a type's shape. Each walks a value structurally — a struct by its fields, an array by its length then elements, an enum by its tag then payload — and refuses a leaf that cannot answer.

- **Equality** — `==` / `!=`, and `<T: Equatable>`. Admits any leaf that is its value; refuses one with no structural equality, an opaque handle or native state (`KSEM390`).
- **Ordering** — `<` / `<=` / `>` / `>=` for the boolean order, and `compare(a, b)` for the three-way [`Ordering`](/docs/language-reference/types) (`Less` / `Equal` / `Greater`), plus `<T: Ordered>`. Refuses a leaf whose only order would be its address (`KSEM391`). `compare` needs Foundation's `Ordering` in scope.
- **Hashing** — `hash(v)`, and `<T: Hashable>`. A deterministic 64-bit FNV-1a fold, consistent with `==`: it admits only leaves whose bits are their value, so two values that are `==` hash the same. A float is refused, because equal floats may differ in bits (`KSEM392`).
- **Tags** — `code(enumValue)` returns an enum's zero-based declaration index; `fromCode<Enum>(n)` rebuilds the variant whose index is `n`, clamping an out-of-range `n` to the first variant. A non-enum, or an enum with a payload-carrying variant, is refused (`KSEM081`).

```kira
struct Point { let x: Int let y: Int }
enum Severity { Note Warning Error }

let same  = Point { x: 3, y: 4 } == Point { x: 3, y: 4 }   // true, no derive
let key   = hash(Point { x: 3, y: 4 })                      // no derive
let order = compare(Severity.Note, Severity.Error)          // Ordering.Less
let sorts = Severity.Note < Severity.Warning                // true
let n     = code(Severity.Warning)                          // 1
let s     = fromCode<Severity>(0)                           // Severity.Note
```

Because ordering compares a value's shape and an unsigned integer is width-erased once it is a leaf, `compare` refuses an unsigned leaf rather than compare it signed. The scalar `<` operator keeps the type, so `<` on a `distinct` over `U32` still gives the typed unsigned order — only the structural three-way `compare` steps back.

## Field Classification

`Serializable` classifies each field. A builtin scalar field (`Int`, the sized numeric widths, `Float`, `F32`, `Bool`, `String`, and the C types) is handled directly. A field whose type is another bare named type is a nested derived type and recurses through that type's own generated function. A missing `serialize_X` surfaces as an ordinary unknown-call diagnostic.

An array field holds scalars, nested arrays, or named derived types to any depth. A generic, optional, qualified, or function field type is refused with a `Diagnostics.error` naming the field. Detection is exact: a type is bare exactly when concatenating its identifiers reproduces its source text.

## Interpolation

Fieldwise interpolation is a plain overload, not a derive. Write `lerp` for a struct by interpolating each field through the ordinary `lerp` overload set — a `Float` field uses Foundation's scalar `lerp`, a vector/color/geometry field uses its own, and a nested struct resolves to the `lerp` written for it:

```kira
struct Point { let x: Float let y: Float }

function lerp(from: borrow Point, to: borrow Point, amount: Float) -> Point {
    return Point { x: lerp(from.x, to.x, amount), y: lerp(from.y, to.y, amount) }
}

let middle = lerp(start, end, 0.5)
```

A field with no matching `lerp` overload fails as an ordinary unresolved overload at that field, which is why interpolation is left explicit rather than invented for discrete values such as `Bool` or `String`.

## The Wire Format

`Serializable` builds on the value-`String` primitives (`String(x)`, `s.count`, `s.charAt`, `s.substring`, `s.indexOf`) and expands into ordinary Kira, so the generated printer and parser are identical on every backend. The format is compact, deterministic, and single-line:

```text
TypeName{field1:VALUE,field2:VALUE,...}
```

An integer writes its spelling around its digits (`U8(7)`, `I32(-5)`), so the value carries its width. A `Float` is `Float(0x` and the sixteen hex digits of its exact bits, an `F32` is `F32(0x` and eight. A `String` is its escaped text wrapped in `"`. An array is its elements in brackets (`[Int(1),Int(2)]`), nested to any depth. A nested derived struct recurses inline, so `from:Point{id:TabId(U32(7))}` sits inside its parent braces. A distinct writes its name around its representation: `TabId(U32(7))`.

Deserialization is the exact inverse. It validates the leading `TypeName{`, then for each field in declaration order locates `label:`, carves the value with a depth-aware scanner, and converts by field type. The integer tag must name the field width exactly, and the digits are range-checked by the narrowing conversion, so `U8(300)` traps and `Int(5)` in a `U8` field is refused. A `U64` field parses unsigned, because the top half of its range is past what a signed accumulation holds.

**Malformed input traps.** A wrong type name, a missing `:` or `,` or `}`, truncated text, trailing text after the closing `}`, a field out of order, a duplicate or unknown label, or a non-digit where an integer is expected drives an out-of-range `charAt` or an inverted `substring`. Both turn into a hard trap on every backend. There is no partial parse: a value either round-trips or the program stops.

**Round-trip law.** For every value `v` of a supported type, `deserialize_T(serialize_T(v))` equals `v` field-wise — checked here with the native `==`, no derive.

```kira
@Derive(Serializable)
struct Point { var x: Int var y: Int }

let wire = serialize_Point(Point { x: 1, y: -2 })   // "Point{x:Int(1),y:Int(-2)}"
let back = deserialize_Point(wire)                    // Point { x = 1, y = -2 }
let ok   = back == Point { x: 1, y: -2 }             // true, native equality
```

## Enums

An enum serializes too, and writes the variant it holds by name, with a payload in parentheses after it.

```kira
@Derive(Serializable)
enum Note { Blank Rank(Int) Tag(String) }

serialize_Note(Note.Rank(42))                       // "Note.Rank(Int(42))"
serialize_Note(Note.Blank)                          // "Note.Blank"
deserialize_Note("Note.Tag(\"edge\")")              // Note.Tag("edge")
```

The variant is named, never numbered. An enum used as a struct field is that same text in the field value slot, and an unknown variant name traps like any other structural violation.

## Two Limits

A `String` value is escaped on the way out and unescaped on the way back: `\"`, `\\`, `\n`, `\r`, `\t`, and `\0`. Everything else is written as itself, and the scanner that carves a field out reads a quoted region as content, so a value holding `;` or `}` round-trips. An escape the format does not define is malformed input and traps, rather than being passed through as text nothing wrote.

A `Float` is written as its bits, not as a rendering of them, so it reads back as itself — including a signed zero, an infinity, and a NaN payload, none of which a decimal form can carry. A decimal wire value would round twice: once writing, once reading.

## Distinct Types

A [`distinct` type](/docs/language-reference/types#distinct-types) works with both the native operations and the remaining derives, and every derive delegates to the representation it was declared over rather than wrapping it.

```kira
@Derive(Serializable)
distinct Port = U32

let same   = Port(U32(41)) == Port(U32(41))   // true, native equality
let key    = hash(Port(U32(41)))              // native hash
let less   = Port(U32(41)) < Port(U32(42))    // true, native unsigned order
let copied = Port(U32(41))                    // a distinct over a scalar is Copy
serialize_Port(Port(U32(8080)))               // "Port(U32(8080))"
deserialize_Port("Port(U32(8080))")           // Port(U32(8080))
```

A distinct type has exactly one readable member, `raw`, and `Serializable` sees it as a field of that name. A distinct over a scalar word is `Copy`, so a plain binding copies it; `Serializable` builds it by calling it, so the wire reader returns `Port(raw)` rather than a brace literal.

`RawPtr` is refused where it has no answer: `Serializable` cannot write an opaque foreign word as a portable value, and the native `hash` and `compare` refuse it too — an address means nothing across runs.

## `@Derive(Copy)`

`Copy` is a compiler builtin rather than a Foundation macro: it generates no code and produces no free function. It is an *opt-in assertion* that a type is structurally copyable, checked at compile time, which is why macro expansion leaves it in place instead of consuming it.

Kira already classifies copyability automatically and structurally: a type is copyable when every field or variant payload is, and it *moves* the moment it gains a heap-owning field (a `String`, an array), an opaque payload (a callback, native state), or anything that transitively contains one. That classification is silent, so adding one such field flips a type from copy to move at every call site with no signal at the declaration. `@Derive(Copy)` makes the contract explicit and enforced.

On an eligible type the derive is a **no-op**: it compiles and the type behaves exactly as before, granting no new powers. On an ineligible one it is `KIR005`, naming the first offending field or variant payload and its type, and the check is transitive.

```kira
@Derive(Copy)                 // ok: every field is a scalar
struct Point {
    var x: Int
    var y: Int
}

@Derive(Copy)                 // error[KIR005]: `Label` derives `Copy`, but its
struct Label {                //   member `text` has type `String`, which is not
    let id: Int               //   copyable, so `Label` moves rather than copies.
    let text: String
}
```

`Copy` composes with the Foundation derives: `@Derive(Copy, Serializable)` runs the builtin assertion *and* generates `serialize_<Type>`. It is recognized before the user-macro lookup, so it never trips `KMAC011`.

`Copyable` is the trait spelling of the same assertion. See [Traits](/docs/language-guide/traits#compiler-known-traits).
