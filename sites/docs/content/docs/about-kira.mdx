Kira is a compiler and runtime toolchain implemented as a Rust workspace. One program runs on a bytecode VM, on LLVM-emitted machine code, on a hybrid of the two, and on `wasm32-emscripten`, and every backend is held to the same answers.

## What Ships in This Repository

| Piece | Crates |
| --- | --- |
| Frontend | `kira-source`, `kira-lexer`, `kira-macros`, `kira-parser`, `kira-semantics`, `kira-ir` |
| VM | `kira-bytecode`, `kira-vm-runtime` |

The full layer graph is in [Compiler Architecture](/docs/appendix/compiler-architecture).

## Backend Parity

A feature is finished when it works on the VM and on LLVM/native, on hybrid where it touches the seam, and on WASM where it is Web-portable. Anything else is refused by a typed diagnostic rather than half-supported on one engine.

That rule is why `crates/kira-cli/tests/backend_parity/` runs the same program on every engine and requires identical output, traps included.

## The Compiler and Library Split

The compiler owns parsing, macro expansion, semantic validation, lowering, and toolchain orchestration. Everything a program's author would call a library lives in Kira source.

Foundation is a real Kira package, not a compiler branch: its derive macros, its `Result`, its filesystem surface, and its image decoders are `.kira` files under `foundation/app/`. Construct families are the mechanism that lets a UI framework be written the same way, which is why `Widget` and `View` appear in Kira source and never in the compiler.
