An annotation is `@Name`, optionally with a payload. Every one the compiler answers to is listed here; there is no `annotation` declaration form, so a program cannot add one. What a program *can* add is a [macro](/docs/macros), which is how `@Derive(Equatable)` and a property wrapper's `@State` exist without a compiler branch.

## Entrypoint and Execution

| Annotation | Where | Meaning |
| --- | --- | --- |
| `@Main` | A function | The program's entrypoint. Exactly one per application (`KSEM011`), none in a library (`KSEM255`), and it takes no parameters. |
| `@MainThreadLifecycle` | A zero-argument `Void` function | A call starts a preserved loop on the process main thread and returns immediately. Its transitive call tree stays on that thread. Multiple instances share main-thread slices and may coexist with `@MainThread` targets. |
| `@MainThread` | A function | The function runs on the operating-system main thread's event loop. Call it through `MainThread.invoke`, `MainThread.spawn`, or `MainThread.post`. It cannot also be `@Main` and is unavailable on WebAssembly. |
| `@Runtime` | A function | On a hybrid build, this body stays bytecode. |
| `@Native` | A function | On a hybrid build, this body compiles to machine code. |

`@Native` on its own is accepted by every engine. The VM compiles every function to bytecode, so the annotation does not request native execution there, and `--backend llvm` makes every body native whether or not it is written. Hybrid is the only build where the split is real. See [Execution Model](/docs/language-guide/execution-model).

## Library Exports

`@Export` names the functions a consumer of a Kira library may call, and the classes whose instances may cross as opaque handles. It is bare: no arguments, no block, no symbol override. See [Library Packages](/docs/appendix/cli/packages).

## Construct Members

These are legal only inside a `construct` body.

| Annotation | Meaning |
| --- | --- |
| `@Required` | On a `let`, a value obligation. On a `function`, a bodyless signature every backed declaration must implement. |
| `@Content` | On a `let`, a child slot filled by a construction's trailing block. The same thing as writing the type `some X`. |
| `@Consuming` | On a `function`, a method that consumes its receiver. |
| `@Comptime` | On a `lifecycle` hook, a hook that runs during compilation instead of at run time. |

Any other `@Name` on a construct member is `KPAR061`.

## The FFI Family

Each of these carries a `{ key: value; … }` block. [Interop and FFI](/docs/language-guide/interop-and-ffi) covers what each block says.

| Annotation | Declares |
| --- | --- |
| `@FFI.Extern` | A bodyless function reaching a C symbol in a named library. |
| `@FFI.Syscall` | A bodyless function reaching a Linux system call, with no library at all. |
| `@FFI.Struct` | A struct laid out the way C lays out its declaration. |
| `@FFI.Pointer` | A typed pointer to a target type, with an ownership mode. |
| `@FFI.Array` | An inline C array of an element type and a fixed extent. |
| `@FFI.Callback` | A C function-pointer type, by ABI, parameter list, and result. |
| `@FFI.Alias` | A transparent alias a generated binding uses for a C typedef. |

## Derives

`@Derive(Name, …)` runs each named derive macro over the declaration below it.

`Copy` is the one derive the compiler answers itself. It generates no code and is an opt-in assertion that a type is structurally copyable, checked at compile time and reported as `KIR005` when it is not. Every other derive is a macro: Foundation ships `Equatable`, `Clone`, and `Serializable`, written in Kira. See [Derives](/docs/macros/derives).

## Documentation

Documentation is not an annotation. Consecutive `///` comments immediately above a declaration are its documentation, and `kira doc` renders them.

```kira
/// Horizontal position in points.
var x: Float = 0.0
```
