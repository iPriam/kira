`construct` defines a **declaration family**: a typed template that other declarations conform to. It is not data (`struct`), not variants (`enum`), and not inheritance-of-behavior (`class`). A construct says *what shape a declaration must have*; concrete declarations headed by the family name (`Widget Button { ... }`) fill that shape in.

This is the surface that lets a library define something like a UI framework — `Widget`, `View`, `Route` — in Kira source rather than hardcoding it in the compiler.

## What executes today

The construct family is **fully parsed and semantically validated**, and a growing slice now **executes on `vm`, `llvm`, and `hybrid`**:

- the `Widget → Node` bridge (computed `let node: T { ... }` accessors) executes
- concrete declarations coerce to `any Family`, and heterogeneous `[Widget]` arrays unify
- caller-provided content trees (`@Content` fields filled by trailing `{ ... }` blocks) construct and execute end to end
- `attempt` / `try` / `handle` executes

Inheritance dispatch, property schemas, required-function satisfaction, content channels, and content composition are **validation-complete** (parse + semantic checks + diagnostics).

## Inheritance: `extends`

Constructs inherit from other constructs with `extends` (not `:`, not `extend`). Multiple parents are allowed; the local inheritance graph must be acyclic.

```kira
construct WebElement {}
construct Drawable {}
construct Surface extends WebElement, Drawable {}
```

A construct-backed declaration may use a **prior declaration** as its parent, inheriting that declaration's family and implementations:

```kira
construct Drawable { requires { function draw() } }
Drawable Sprite { function draw() {} }   // first concrete child must implement draw()
Sprite Player {}                          // inherits draw()
Sprite AnimatedPlayer { function draw() {} }  // overrides draw()
```

Diagnostics: unknown parent (`KSEM118`), inheritance cycle (`KSEM119`).

## Property schemas

A construct declares a typed property schema. `required` properties must be provided by every declaration; others are optional. Properties are inherited through `extends`.

```kira
construct WebElement {
    properties {
        id: String
    }
}
construct Route extends WebElement {
    properties {
        required path: String
        title: String
    }
}
```

Declarations supply properties through a **section**, never a constructor-style call:

```kira
Route Home {
    properties {
        path: "/"
        id: "home"
    }
}
```

Diagnostics: missing required property (`KSEM123`), unknown property (`KSEM124`), property type mismatch (`KSEM125`), duplicate property (`KSEM126`).

## Required functions

`requires { function ... }` lists functions the family's first concrete declaration must implement. A required function returning `Result<Value, Failure>` is fallible. `Self` refers to the implementing declaration's type. An "interface-like" construct is a `requires`-only construct.

```kira
construct WebElement {
    requires {
        function render() -> Result<DomNode, RenderFailure>
        function update(previous: Self)
        function unmount()
    }
}
```

Diagnostics: missing required function (`KSEM120`), signature mismatch (`KSEM121`).

## The SwiftUI-style surface: `@Required` and the `node` bridge

Alongside the section surface, a construct may declare **direct members** at its body's top level — requirements written as members rather than in a separate `requires { ... }` block.

- `@Required let name: T` — a field every concrete declaration must provide.
- `@Required function f(...) -> T` — a required behavior (a bodyless signature), checked like `requires`.
- `let name: T { ... }` — a **computed default member** (a block-bodied field), not stored state. Declarations may override it.

```kira
construct Node {
    @Required function measure(proposal: SizeProposal) -> Size
    @Required function place(bounds: Rect) -> PlacedNode
}

construct Widget {
    @Required let body: Widget
    let node: Node { body.node }   // default Widget->Node bridge; composites inherit it
}
```

A concrete declaration uses the family name directly. Component inputs are ordinary `let` fields; the typed bridge to the layout layer is `let node: Node { ... }`.

```kira
// Composite widget: provides `body`, inherits the default `node = body.node`.
Widget Button {
    let title: String = ""
    let body: Widget {
        Text(text: title)
    }
}

// Primitive/terminal widget: provides `node` directly and omits `body`.
Widget Text {
    let text: String = ""
    let node: Node {
        TextNode(text: text)
    }
}
```

**Terminal-`node` rule.** A required field need not be provided when the declaration overrides every default member that consumes it. Because the default `node` reads `body`, an explicit `node` discharges the required `body`, and node resolution stops at the explicit `node` instead of recursing through `body`. A declaration that provides neither `body` nor `node` is rejected.

Member access without parentheses (`widget.node`, `button.body.node`) invokes the computed accessor; accessor chains compose. This bridge executes on `vm`, `llvm`, and `hybrid`.

Diagnostics: missing required member (`KSEM140`); a `body` that expands to itself without a terminal `node`, which would resolve forever (`KSEM141`).

## Caller-provided content: `@Content`

A concrete declaration marks caller-provided children as `@Content` fields. **Field names are the channel names** — there are no string-labeled channels. A trailing `{ ... }` block on a construction fills them, resolved by inspecting the callee:

- one `@Content let x: Widget` → a bare block holds **exactly one** child
- one `@Content let xs: [Widget]` → a bare block holds an **ordered list** of children
- several `@Content` fields → a bare block is ambiguous; children are supplied as **named fills** using the field names (declaration order is preserved)

```kira
Widget VStack {
    @Content let children: [Widget]
    let node: Node { VStackNode() }
}

Widget Padding {
    @Content let child: Widget
    let node: Node { PaddingNode() }
}

Widget Dialog {
    @Content let header: Widget
    @Content let content: Widget
    let node: Node { DialogNode() }
}

Widget Screen {
    let body: Widget {
        VStack {
            Text(text: "title")
            HStack {
                Text(text: "left")
                Text(text: "right")
            }
            Dialog {
                header { Text(text: "Title") }
                content { Text(text: "Message") }
            }
        }
    }
}
```

Children are stored as `any Widget`, and these caller-provided trees **construct and execute** (nested lists, single children, and named fills) across `vm`, `llvm`, and `hybrid`.

Diagnostics: a trailing block on a declaration with no `@Content` field (`KSEM142`); wrong child count for a single-`Widget` field (`KSEM143`); a bare block where named fills are required (`KSEM144`); a non-widget child (`KSEM145`).

## Fluent modifiers: `extend`

`extend C { ... }` adds fluent modifier functions to a family — the external, chainable surface (`.padding(...)`), distinct from the core `node` bridge. Modifiers return the family type and wrap the receiver via `self`.

```kira
extend Widget {
    function padding(amount: Float) -> Widget {
        Padding(amount: amount) {
            self
        }
    }
}

Widget Button {
    let title: String = ""
    let body: Widget {
        Text(text: title).padding(amount: 8)
    }
}
```

Diagnostics: extending an unknown construct (`KSEM146`). Modifier bodies and construction sites are validated before any backend.

## Content channels

A construct's `content { ... }` block declares named content channels. `accepts` constrains the element type; `count` (a `min..max` or `min..` range) constrains how many elements a declaration may place. Channels are inherited through `extends`.

```kira
construct WebElement {
    content {
        head { accepts Title; count 0..1 }
        body { accepts Title; count 1.. }
    }
}
```

A declaration fills channels with named sections:

```kira
Document Page {
    head { Title("Home") }
    body {
        Title("Welcome")
        Title("More")
    }
}
```

Content-requiredness is expressed through `count 1..` (reported as `KSEM129` when a channel is left empty) — `requires` declares required *functions* only.

Diagnostics: unknown channel (`KSEM127`), count violation (`KSEM129`), accepts mismatch (`KSEM130`), duplicate channel (`KSEM138`).

### Content composition

A construct may compose inherited content:

- `content sealed` — closes the content surface; descendants may not add/refine/project.
- `content refine { channel { … } }` — narrows an inherited channel (count must stay within the inherited range; `accepts` may not change element type).
- `content passthrough` — forwards the parent's channels; the construct owns none of its own.
- `content project { local as Parent.channel }` — maps a local section name onto an ancestor's channel.

```kira
construct Route extends WebElement {
    content project {
        view as WebElement.content
        header as WebElement.head
    }
}
```

Diagnostics: content into a sealed construct (`KSEM128`), unknown projection target (`KSEM131`), invalid composition such as a widening refine or a meaningless passthrough (`KSEM132`).

## Linear error handling: `attempt` / `try` / `handle`

`attempt` / `try` / `handle` unwraps `Result<Value, Failure>`. Inside an `attempt` block, `try expr` yields the `Ok` value and continues; on `Error`, control transfers to the matching `handle` case, selected by the failure's variant. `try` is valid only inside `attempt` (`handle` is a contextual keyword). This **executes** on `vm`, `llvm`, and `hybrid` by desugaring to enum `match`.

```kira
attempt {
    let node = try element.render()
    append(target, node)
} handle {
    MissingNode(reason) {
        Log.error(reason)
    }
    InvalidState {
        Log.error("invalid state")
    }
}
```

A `handle` case may bind and read the failure's payload. All `try`s in one `attempt` must share a single failure enum.

Diagnostics: `try` outside `attempt` or in an unsupported position (`KSEM133`); `try` on a non-`Result` value (`KSEM134`); a missing handle case for a reachable failure variant (`KSEM135`); a handle case that is not a variant of the failure enum (`KSEM136`); incompatible failure enums across one `attempt` (`KSEM137`).

## Why constructs matter

Constructs are the clearest example of Kira's intended boundary:

- the compiler provides mechanisms and validation
- higher-level framework behavior (the actual UI library, themes, diffing) stays in Kira source
- annotations are declared as source symbols; constructs decide their domain-specific meaning

That boundary is what lets a UI-style construct keep real child trees for layout and rendering while staying out of the compiler core.
