`async function` marks a task entry point: a body that is *spawned* with `Task { … }` and joined for its result. It is not a function to call: a direct call is `KSEM354`, and only an `async function` may be a task target (`KSEM352`). Its parameters are taken owned or copied, never borrowed (`KSEM353`), because the task runs after the caller's places may be gone. `async` is contextual, so a local named `async` still binds.

`Task { work(a, b) }` spawns a deferred task and hands back an opaque handle. The arguments evaluate at the spawn; the body runs at the first drive.

```kira
async function total(a: Int, b: Int) -> Int { return a + b }

@Main function main() {
    let handle = Task { total(40, 2) }
    print(handle.await)          // 42, the call ran here rather than above
    return
}
```

## The Handle

A handle has exactly three operations, and anything else on one is `KSEM158`.

| Written | What it does |
| --- | --- |
| `handle.await` | Drives the task to completion and takes its result. A `Void` body joins as `Int` `0`, so a join is always a value. |
| `handle.requestCancel()` | Asks a task that has not run yet not to. Its body never runs, and awaiting it afterwards traps. |
| `handle.detach()` | Drives the task and throws the result away. Awaiting a detached task traps, as does joining any task twice. |

## Yielding and Sleeping

`taskYield()` is a cooperative suspend point: it hands the oldest queued task a turn and comes back. With nothing queued it does nothing, so calling it outside a task body is legal.

`taskSleep(ms)` moves a **virtual** clock forward and then yields. Nothing sleeps in real time, so a program orders its tasks the same way on every backend and a test suite never waits.

## What a Task Body May Be

A call to an `async function` taking `Int` or `Float` parameters and returning `Int`, `Float`, or nothing, chosen among overloads exactly as an ordinary call is, or a bare numeric literal (`Task { 41 }`). Anything else is `KSEM159`. That restriction is what lets a spawn evaluate its arguments now and its body later with no closure in between.

## The `Send` Rule

A spawn is the one boundary a value crosses without its spawner, so what the deferred call takes and returns must be [`Send`](/docs/language-guide/traits#what-carries-send-and-sync) (`KSEM312`). The slot rule above is narrower today, and every type it admits is `Send`.

## The Scheduler

The scheduler is generated IR, not runtime code. The compiler synthesizes the spawn, dispatch, join, detach, cancel, yield, and sleep helpers, and they reach the task table through one primitive. The VM and the native backend therefore run the same scheduler rather than two that have to be kept in step.

The task table belongs to one run. A VM creates it when execution starts; a
native or hybrid host resets its thread-local table at the same boundary and
clears it when the run ends. A task handle is therefore never valid in a later
run, even when a hybrid library stays loaded between runs.

Handles include a slot generation. Joining, detaching, or cancelling reclaims
the task's table storage; a later spawn may reuse that storage, but the old
handle cannot name the new task. Runnable tasks are selected in spawn order.

## Channels

A channel is an ordered handoff between two contexts. It answers the question a
program cannot otherwise ask: how its own work orders against work already
running somewhere else. Without one, an outsider can only enqueue.

`Channel<T>()` creates a channel and hands back its **sender**. The matching
**receiver** is read off it as `.receiver`, which is a derivation rather than a
second creation: there is one channel however many times it is read.

```kira
async function fill(tx: Sender<Int>) -> Int {
    tx.send(41)
    tx.send(1)
    tx.close()
    return 7
}

@Main function main() {
    let tx = Channel<Int>()
    let rx = tx.receiver
    var pending = Task { fill(tx) }
    attempt {
        let first = try rx.receive()
        let second = try rx.receive()
        print(first + second)          // 42, after `fill` ran
    } handle {
        Closed { print(0 - 1) }
    }
    print(pending.await)
    return
}
```

### The Two Ends

`Sender<T>` and `Receiver<T>` are two types, and neither is the number
underneath. Passing a receiver where a sender belongs is a type error rather
than a direction caught at run time.

| Written | On | What it does |
| --- | --- | --- |
| `sender.send(value)` | sender | Puts one value behind every value waiting. |
| `sender.receiver` | sender | The matching receiver end. |
| `receiver.receive()` | receiver | The next value, waiting for one if none is there. |
| `end.close()` | either | This end is done. |

Anything else on an end is `KSEM367`, including `.raw`: an end is opaque, and
the handle underneath would let a program forge one.

### Receiving Waits

`receive()` is a suspension point. An empty channel whose sender is still live
hands the next runnable task a turn and asks again, so a receive orders the
receiving context after the work that fills it. A receive that did not yield
would be a deadlock written as a loop.

Because it waits and can fail, `receive()` is a fallible step written under
`try` inside an `attempt`, like every other one.

### A Closed Channel Is Not a Trap

The sender being gone is an ordinary end to a conversation. A receive on a
drained closed channel answers `ChannelError.Closed`, which the enclosing
`handle` covers by name. Sending to a channel whose receiver is gone *is* a
trap: the value has nowhere to arrive and nobody to tell.

### A Receive Nothing Can Answer Is a Trap

A receive on an empty live channel with nothing left to run traps with
`a receive is waiting for a value nothing can send`. The queue is empty, the
sender is still live, and no other work is runnable, so no later turn can
change the answer.

It is not reported as `Closed`. That would tell the program the sender went
away when it did not, and a handler written for the end of a conversation would
run for a program that never started one. It is not a wait either: waiting
forever is a hang, and a hang is not an answer.

Cancelling the task that would have filled a channel produces exactly this. The
receive learns that its value is not coming instead of blocking on work that
was called off.

```kira
@Main function main() {
    let tx = Channel<Int>()
    let rx = tx.receiver
    var filler = Task { fill(tx) }
    filler.requestCancel()             // the only work that could send it
    attempt {
        let value = try rx.receive()   // traps: nothing can answer this
        print(value)
    } handle {
        Closed { print(0 - 1) }
    }
    return
}
```

### What a Channel May Carry

A payload must be `Send`: it leaves the context that sent it and arrives in one
that context does not own, so a value naming storage its own engine keeps is
refused with `KSEM312`. That covers a capture cell, a native-state handle, a
row in an executor's table, and a function type, which says nothing about what
a closure of it captured.

Anything `Send` may cross, including a `String`, a struct, an array and an
enum. A queue slot is one machine word, so a scalar *is* that word and a value
that owns storage travels as a token naming it — the sender gives the value up
and the receiver takes it out, so what arrives is the value itself rather than
a share of the sender's.

Two things have nothing a slot can name, and both are `KSEM365`. `Void` is a
value that is not there, so there would be nothing for `send` to take and
nothing for `receive` to answer with. A pointer word names storage on the far
side of a seam this language does not read, so what arrived would be an address
whose meaning stayed behind.

A `Float` crosses as its exact bits and is converted at both ends, so it reads
back as itself. A `distinct` keeps its identity: what comes out is the named
type that went in.

```kira
let tx = Channel<String>()
let rx = tx.receiver
var filler = Task { send(tx) }
attempt {
    print(try rx.receive())     // the string itself, not a view of it
} handle {
    Closed { print("done") }
}
```

Closing a receiver discards whatever is still queued, and a queued payload that
owns storage is released as it goes — a `close()` on a channel nobody drained
frees every value still waiting in it.

`Sender<T>` and `Receiver<T>` are the same channel written as an annotation, so
a payload a channel may not carry is refused where the annotation is written,
under the same code.

An end is one word, which is what a task argument slot holds, so an end is
moved into the task that uses it the way any other scalar is.

### The Wait Is Generated IR

Like the scheduler, the waiting policy is synthesized IR rather than runtime
code: one function per payload type, reaching the channel table through one
primitive. The VM and the native backend run the same wait rather than two that
have to be kept in step.

The channel table belongs to one run, exactly as the task table does, and an
end handle carries a slot generation. Closing both ends reclaims the storage; a
later channel may reuse it, but the old end cannot name the new channel.

A `@MainThreadLifecycle` loop is one execution however many slices it runs in,
so the channels and tasks it made are still its own after every suspension. An
end taken before a slice boundary names the same channel after it.

## Host Main Thread

`@Main` runs on Kira's helper thread. A framework that must use the operating-system main thread marks its target `@MainThread` and requests it with one of three explicit operations:

```kira
@MainThread function makeView(text: String) -> String { return text }

@Main function main() {
    let view = MainThread.invoke { makeView("Kira") }
    let later = MainThread.spawn { makeView("later") }
    MainThread.post { makeView("notification") }
    print(later.await)
    print(view)
    return
}
```

`invoke` waits for the target and returns its value. `spawn` queues it and returns a handle whose only operation is `.await`. `post` queues it without a result. The event loop continues to service accepted posts and spawned work while the helper is running. Arguments and results are owned copies and must be `Send`; borrowed mutable parameters are not available across this boundary. Direct calls from the helper to an `@MainThread` function are rejected, and WebAssembly rejects the annotation because it has no process main thread.

Use `@MainThreadLifecycle` for a preserved event loop that shares the process main thread with other lifecycles and `@MainThread` work. Start it by calling the lifecycle from `@Main`. The call queues a new instance and returns `Void`; the instance keeps its locals and call stack between cooperative slices. A stalled application thread cannot stop an already-started lifecycle.
