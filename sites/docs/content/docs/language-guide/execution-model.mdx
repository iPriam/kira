One program, four engines.

| Engine | What runs | Selected by |
| --- | --- | --- |
| VM | bytecode, interpreted | `--backend vm`, the default |
| LLVM/native | machine code with DWARF | `--backend llvm` |
| hybrid | bytecode plus a loaded native half, in one process | `--backend hybrid` |
| Web | the LLVM lowering, through emscripten | `--device wasm32` |

## The Shared Pipeline

```text
source -> lexer -> macros -> parser -> semantics -> IR -> backend
```

Every backend consumes the same IR. Macro expansion, import resolution, generics, closures, construct families, and trait existentials are all resolved above that line, so a backend never learns they existed. That is why a feature lands on every engine at once rather than one at a time.

## `@Runtime` and `@Native`

On hybrid, and only on hybrid, the two annotations are real: a `@Runtime` body stays bytecode and a `@Native` body compiles to machine code, and both run in one process through the bridge.

- The VM compiles every function to bytecode, so `@Native` requests nothing there.
- `--backend llvm` compiles every function to machine code, so `@Runtime` requests nothing there.

Neither annotation is contagious. A `@Runtime` function calls a `@Native` one directly and a `@Native` function calls back into `@Runtime`, both through generated trampolines. Values crossing are marshalled as described in [Crossing the Native Seam](/docs/language-guide/structures-and-types#crossing-the-native-seam).

A system call is an instruction, so a body holding one has to be native. `--backend llvm` needs nothing said; on hybrid, `packages/linux` carries `@Native` on every function so the instruction lands where an instruction can live.

## The Main Thread Event Loop

Native process entry starts a synchronous event loop on the operating-system main thread. Kira's `@Main` function runs on a named `kira-helper` thread, so a slow Kira operation does not stop a UI framework that owns the process main thread.

`@MainThreadLifecycle` marks a zero-argument `Void` function that runs as a long-lived main-thread loop. `@Main` starts it with an ordinary-looking call:

```kira
function createApplication() -> Int {
    return 1
}

@MainThreadLifecycle function applicationLifecycle() {
    let application = createApplication()
    runApplication(application)
    return
}

@Main function main() {
    applicationLifecycle()
    return
}
```

Calling a lifecycle schedules a new instance and returns `Void`; it does not run the body on the application thread. Each instance keeps its call stack and locals between turns. Its ordinary transitive call tree stays on the process main thread, including calls crossing the runtime/native boundary in a hybrid build.

Started lifecycles share the main thread in cooperative slices. One lifecycle receives every lifecycle slice. Multiple lifecycles take turns, with accepted `@MainThread` work serviced between them. Returning ends that instance. The process main-thread loop remains alive after `@Main` returns until every started lifecycle returns.

The application thread and main-thread loop are structurally separate. A stalled `@Main` body cannot stop an already-started lifecycle. `@MainThreadLifecycle` and `@MainThread` may coexist: use lifecycle calls for preserved event loops and `MainThread.invoke`, `spawn`, or `post` for one-off main-thread work.

`@MainThread` marks a function that a framework requires on the operating-system main thread. The helper asks for that function explicitly:

```kira
@MainThread function createWindow(title: String) -> Int {
    return 1
}

@MainThread function present(window: Int) {
    return
}

@Main function main() {
    let window = MainThread.invoke { createWindow("Kira") }
    let shown = MainThread.spawn { present(window) }
    MainThread.post { present(window) }
    shown.await
    return
}
```

`invoke` runs the target synchronously and returns its value. `spawn` queues the target and returns an opaque handle; `.await` drives that work and returns the target value. `post` queues fire-and-forget work and returns immediately after the event loop accepts it. Arguments and returned values are owned copies, and every value crossing the boundary must be `Send`. A target cannot use `borrow mut` writeback across the boundary.

The annotation is an execution contract, not a framework choice. Kira does not choose priorities or name a UI toolkit. From the helper context, an annotated function is reachable only through `MainThread.invoke`, `MainThread.spawn`, or `MainThread.post`; a direct helper call is rejected. `@Main` and `@MainThread` cannot decorate the same function. This capability is unavailable on WebAssembly because a Web build has no Kira process main thread.

## Standalone Hybrid Programs

`kira build --backend hybrid` produces something the operating system starts, not just a bundle for `kira` to host. The deployment is four files:

```text
.kira-build/<name>            the standalone executable
.kira-build/<name>.khm        the manifest tying the halves together
.kira-build/<name>.kbc        the bytecode half
.kira-build/lib<name>.dylib   the native half (.so on Linux, .dll on Windows)
```

The executable is a copy of Kira's hybrid launcher: it loads the manifest beside itself and runs the program through both engines exactly as `kira run --backend hybrid` does in-process.

```bash
./.kira-build/<name>              # uses the .khm beside it
./.kira-build/<name> other.khm    # or name a manifest explicitly
```

Everything after an explicit `.khm` path is passed to the program as its arguments. The directory is the deployment unit: move the four files together, under any names, and the program still runs. If several `.khm` files sit beside the executable, pass the one you mean; if none does, the launcher says so rather than guessing.

## The Web Engine

The Web target runs the same LLVM lowering the host does, through emscripten. The portable VM core builds for `wasm32-unknown-unknown` separately, which is what lets a Kira library run inside a browser tab with no linker at all. See [Web and WASM](/docs/appendix/platforms/web-and-wasm).

## Backend Parity

A feature works on the VM and on LLVM/native, on hybrid where it touches the seam, and on WASM where it is Web-portable, or it is refused by a typed diagnostic. `crates/kira-cli/tests/backend_parity/` runs the same program on each engine and requires identical output, traps included.

Where an engine has something another does not, the manual says so rather than quietly weakening the claim. A native library's `print` goes to stdout with no host to redirect it; a trap ends the process; and two Kira native libraries cannot share one binary.

## Trap Behavior

A trap is a hard stop with the same cause on every engine: an out-of-range index, a `charAt` past the end of a string, an inverted `substring`, an over-long `@FFI.Array` fill, awaiting a cancelled or already-joined task. A trap in a built native program ends the process, exactly as it ends a VM run. `attempt`/`try`/`handle` is the portable way to keep a failure away from a boundary that cannot take one.
