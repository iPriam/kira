A Kira program is a directory of `.kira` files. One of them declares `@Main`.

```kira
@Main
function main() {
    let left = 40
    let right = 2
    print(left + right)
    return
}
```

## The Entrypoint

An application declares exactly one `@Main` (`KSEM011`) and it takes no parameters. A library declares none (`KSEM255`), and `kira run` on one is refused because there is no way in.

`kira` finds the package by walking up from the source file for a `package.kira`, so the manifest decides whether a directory is an application or a library and no flag can disagree with it. A `.kira` file with no manifest above it is a program.

## Comments

```kira
// a line comment
/// a documentation comment, read by `kira doc`
```

Consecutive `///` comments above a declaration are its documentation. `kira doc` renders them as Markdown.

## Local Bindings

`let` binds once; `var` may be reassigned.

```kira
let total = 42          // inferred from the initializer
var label: String       // declared, not yet usable
var ratio: Float = 0.8  // the initializer must already match
```

A declaration with no initializer stays uninitialized until an assignment gives it a value, and reading it earlier is refused. An annotated initializer is strict: `var ratio: Float = 0` is rejected because an integer literal is not a `Float`.

## Module Constants

`let` at module scope declares a constant: one value per program, computed once at program start — before `@Main` runs — and shared by every reader.

```kira
let answer = 6 * 7
let greeting = "hello " + audience()
let table = buildTable()

function audience() -> String { return "world" }

function buildTable() -> [Int] {
    var xs: [Int] = []
    xs.append(answer)
    return xs
}
```

The initializer is an ordinary expression and may call functions, so a value that is expensive to build — a parsed table, a decoded resource — is built once instead of at every use. Declaration order does not matter: each constant is evaluated after the constants it depends on, and a dependency cycle is refused (`KSEM317`).

Constants share one namespace with top-level functions (a collision is `KSEM316`), a local of the same name shadows one inside a body, and there is no module-scope `var` — a program-wide mutable binding would be shared mutable state with an observable initialization order.

## Statement Terminators

A statement ends at a newline or at a `;`. Both spellings are accepted everywhere and mean the same thing.

## Imports

```kira
import geometry as Geo
import shapes.Rect as Rect

@Main
function main() {
    let origin: Geo.Point = Point { x = 0, y = 0 }
    print(Rect.area(origin))
    return
}
```

A module name is a name, not a path: no slashes, no extension, no `..`. One segment is a sibling file (`geometry` is `geometry.kira`); a dot is a directory separator (`shapes.Rect` is `shapes/Rect.kira`). Both resolve against the entry file's directory, and an import naming no readable file is `KSEM032`.

**Imports are file-scoped.** An import written in `main.kira` says nothing about `geometry.kira`. Naming a namespace root this file did not import is `KSEM027` even when a sibling imported it.

What an import binds is a namespace root: the `as` name, or the module's last path segment. The root qualifies names the module declares, so `Geo.Point` and `Rect.area(p)` work. It is not a visibility gate: a package's top-level declarations are visible bare everywhere in the package, and the qualifier is how a reader sees where a name came from.

Two modules that import each other are a legal program. Loading is visited-set-guarded, so a cycle terminates and each file lands in the program once.

`import Foundation` resolves to the standard library beside the compiler. See [Foundation](/docs/foundation).

Imports are resolved entirely in the frontend. By the time the IR exists a program is one flat list of functions, so no backend learns it was ever more than one file.
