Kira calls prebuilt C functions with no `@Native` and no glue: a package lists its native libraries, declares bodyless `@FFI.Extern` functions, and calls them like any other Kira function. The same package runs identically on the VM, on LLVM/native, and on both halves of hybrid, and links for wasm.

`examples/ffi` is the worked example. [FFI Workflows](/docs/appendix/ffi-workflows) covers manifests, generated bindings, C-layout structs, callbacks, and system calls.

## Declaring an Extern

An `@FFI.Extern` declaration names the native library, the C symbol, and the C ABI, and its function has an exact-width signature and no body.

```kira
@FFI.Extern { library: ffimath, symbol: ffi_add, abi: c }
function add(a: I32, b: I32) -> I32

@Main function main() { print(add(20, 22)) return }
```

The three fields are required exactly once, and `abi` must be `c`. Repeatable `retains: <parameter>` fields mark parameters whose C callee keeps pointers after the call. A foreign declaration may not also be `@Main`, `@Runtime`, `@Native`, or `@Export`.

Several C functions from one library may use the grouped shorthand when each Kira function name is also the C symbol name:

```kira
extern library ffimath {
    function add(a: I32, b: I32) -> I32
    function negate(value: I32) -> I32
}
```

Each member is equivalent to an `@FFI.Extern` declaration with `library: ffimath`, `symbol:` equal to the function name, and `abi: c`. Use standalone `@FFI.Extern` when the C symbol differs from the Kira name or when the declaration needs fields such as `retains`.

Two declarations may name the same C symbol, which is what a generated binding beside a hand-written one produces. They must agree on the ABI, the parameters, the result, and which parameters are retained: the linker binds one address, and each call site marshals for whichever declaration it resolved, so a disagreement is two contracts for one function that nothing downstream can catch.

## Taking a Symbol's Address

One Kira name may be declared several times for one symbol, and that is how a symbol with no single C type is bound. `objc_msgSend` is the case: it is not variadic on arm64, so every selector it dispatches must be called through the prototype that selector actually has. The declarations must agree on the library, the symbol and the ABI, and each must differ from the others in its signature.

```kira
@FFI.Extern { library: objc, symbol: objc_msgSend, abi: c }
function msgSend(receiver: RawPtr, selector: RawPtr) -> RawPtr

@FFI.Extern { library: objc, symbol: objc_msgSend, abi: c }
function msgSend(receiver: RawPtr, selector: RawPtr): Void

@FFI.Extern { library: objc, symbol: objc_msgSend, abi: c }
function msgSend(receiver: RawPtr, selector: RawPtr, index: U64) -> RawPtr
```

A call picks one shape by asking three questions in order, and each is only asked because the one before it left more than one answer:

1. **How many arguments were written.** This settles most calls.
2. **What those arguments are.** Two shapes of one selector rarely take the same types.
3. **What the caller expects back.** Shapes that take the same arguments and differ only in what they answer with are separated by nothing else. A call on a line by itself expects nothing, so it means the shape that answers `Void`; an `if` condition expects `Bool`; a binding with a type annotation expects that type.

A call that leaves more than one shape standing after all three is refused rather than guessed at, and the refusal lists what the surviving shapes answer with. Annotate what the call produces to settle it.

`@FFI.Address` names a data symbol rather than a function. It takes no parameters and answers `RawPtr`: the address of the object, not what is stored at it. Reading the object is `@FFI.Pointer`'s job, through the pointer this hands back.

```kira
@FFI.Address { library: sokol, symbol: sapp_desc_default }
function sappDescDefault() -> RawPtr
```

The block carries no `abi`, because nothing is called and there is no calling convention to name.

## The Supported Type Surface

Parameters and results may be `Void`, `Int` and the narrower integers `I8`/`I16`/`I32` and `U8`/`U16`/`U32`/`U64`, `Bool`, `Float` and `F32`, and `RawPtr`.

`Int` crosses as `int64_t` and `Float` as `double`. They *are* the 64-bit types, so nothing is left unsaid by writing them, and a narrower C type still names its width. A Kira `String` in a signature is refused.

### `Bool`

`Bool` crosses as C `_Bool`: **one byte holding `0` or `1`**, `1` byte of size and `1` of alignment wherever it sits, including as a member of a C-layout struct.

Kira writes `0` or `1` and nothing else, so C may compare the object to `1`, index with it, or copy it into another `_Bool` exactly as C code would. In the other direction Kira reads **any nonzero byte as `true`**, which is what `if (b)` means in C. That matters because a `_Bool` outside `{0, 1}` is undefined in C, so a library that writes one has already left the standard: reading the low bit and reading the whole byte then answer differently, and two engines answering differently would be a wrong value rather than a refusal. Every engine reads the byte.

### `CString`

`CString` is C text, and how long its storage lives depends on where it is written.

As a **parameter**, a call passes a Kira `String` (the one implicit coercion), and the bytes are copied into transient NUL-terminated storage for the duration of the call. The caller keeps its `String`, and an interior NUL byte is a typed trap rather than a truncated string. As a **result** or a callback argument, the C bytes are validated: a `String` holds UTF-8 and nothing else, so a C string that is not valid UTF-8 is a foreign-contract trap on every engine, never a lossy rendering. `CString` is illegal in an ordinary Kira local or function parameter.

As a **result**, the seam copies the returned `const char*` into an owned Kira `String` while the pointer is valid, so no C storage crosses the result boundary.

As a **member of a C-layout struct**, it is an owning C-block slot. The block is cloned when the value is copied, moved when the value is bound, and freed when the value dies. A member left out of the literal zero-fills to `NULL`, which is different from a pointer to `""`.

### `RawPtr`

`RawPtr` is an opaque target-width word. Kira may store it, return it, and pass it back to C, but never dereferences it, does arithmetic on it, or frees it: a library that allocates must expose an explicit free extern.

`RawPtr.null` is the null pointer, and `==` and `!=` compare two pointers as the words they are. A C API answers `NULL` for "no adapter", "no window", "the chain ends here", so testing for it is ordinary work rather than a cast:

```kira
let event = ffiEventCurrent()
if event == RawPtr.null { return 0 }
```

A named pointer type is the same word wearing a name, so an `@FFI.Pointer` type, a `distinct` over `RawPtr`, and a plain `RawPtr` all compare to `RawPtr.null` and to each other. Two `distinct` pointer types compare only to themselves, as every `distinct` does. A pointer has no ordering: C defines `<` only between two pointers into one object, and Kira has no arithmetic that could produce such a pair. A pointer does not compare to an integer either; `rawPointerWord(p)` reads the word when a program wants the number.

A pointer member of a C-layout struct that a literal leaves out zero-fills to the null, so `descriptor.next == RawPtr.null` is how a program asks whether it was filled in.

## Foreign Lifetimes

Foreign parameters borrow by default. Storage materialized for a `CString`, a C-layout image, or an array buffer stays live through the call and is freed when its owning value dies, so a per-frame descriptor releases its C blocks every frame.

Use `retains:` only when C keeps an argument after return. It may name a pointer, a `CString`, a C-layout struct, or a `NativeState<T>` owner. C storage moves to the engine's retained registry. A retained `NativeState<T>` instead transfers that affine owner directly to C, which later returns the token or releases it through the callback-state API. A number or a `Bool` carries nothing C can keep by ownership, so `retains:` on one is refused rather than making the call site `move` a value for nothing.

```kira
@FFI.Extern {
    library: sokol,
    symbol: sapp_run,
    abi: c,
    retains: desc
}
function sappRun(desc: SappDescPtr) -> Void

let desc = SappDesc { windowTitle = "Kira" }
sappRun(move desc)
```

A retained named argument requires `move`. C-block ownership moves to the engine registry. A retained `NativeState<T>` is different: the call transfers exactly the moved state reference to C and the engine keeps no hidden second owner. If the call fails before C receives the argument, Kira releases the owner normally. C balances that transferred owner through the callback-state runtime ABI (`kira_rt_native_state_release`); Kira source cannot manufacture or destroy ownership through a `RawPtr`. Retained C-block roots and their child blocks are reported by native heap accounting.

C blocks are uniquely owned and have no share count. C-layout values move on binding, while an explicit copy builds independent blocks and rewrites every embedded child address.

## How One Declaration Serves Every Backend

Every backend reaches C through one generated **adapter** per import: a uniform `extern "C"` entry point that validates the argument tags, narrows and sign- or zero-extends at the C boundary, rounds `F32`, builds and frees transient `CString` storage, calls the real C symbol, and writes back a checked result.

- **LLVM/native** links the selected C archive into the executable and calls the adapter directly.
- **The VM** stays a portable core: it marshals a foreign call to borrowed arguments and asks its host, loading and linking nothing itself. A VM build emits a one-file adapter *sidecar*, the adapters plus the C archive, and the CLI's native-capable host answers `call_foreign` out of it.
- **Hybrid** links the C archive and the adapters into its one native half. A `@Runtime` function's foreign call runs through the VM half's `call_foreign` and a `@Native` function's runs as machine code, and both reach the *same* copy of the C library, never a second `dlopen`. The example's counter proves it: a runtime-half call and a native-half call count 1 then 2, not 1 then 1.

## Opaque Callback State

For a native API that carries a `void*` userdata token, these intrinsics move Kira-owned state across it without exposing a layout.

| Written | What it does |
| --- | --- |
| `nativeState(value)` | Boxes a Kira value and returns one affine `NativeState<T>` owner. |
| `nativeUserData(owner)` | Clones a tracked owner. The result is another `NativeState<T>`, not a `RawPtr`. |
| `nativeUserDataBorrow(owner)` | Borrows the owner's opaque userdata word as `RawPtr`. The word owns no reference by itself. |
| `nativeRecover<T>(ownerOrToken)` | Borrows typed mutable access to the stored state from a tracked owner or a borrowed raw token. |
| `nativeUserDataRetain(...)` | Refused in Kira source. An owner with no affine value would make its release obligation invisible. |
| `nativeUserDataRelease(owner)` | Consumes one tracked `NativeState<T>` owner. `RawPtr` is refused. |

`NativeState<T>` is an affine ownership type and may be written in parameters and aggregate fields. Moving it transfers exactly one owner, scope exit releases that owner, and `nativeUserData(owner)` is the explicit operation that creates another compiler-tracked owner. Kira does not implicitly erase an owned state into `RawPtr`, because a copyable pointer word cannot carry the release obligation. In a hybrid build, `NativeState<T>` parameters and results cross the `@Native`/`@Runtime` boundary as tracked owners of the same callback-state token. A borrowed parameter keeps the caller's owner, while `move` transfers one owner to the other engine.

Callback state preserves ownership recursively. A boxed value may contain another `NativeState`, and structs nested anywhere in the value may implement `Drop`. Replacing a recovered field releases the displaced value immediately. Final state release runs every nested `Drop` body and nested state release in the same reverse-field order as an ordinary Kira value on VM, LLVM/native, and hybrid.

`nativeUserDataBorrow(owner)` is the FFI view. Its `RawPtr` is valid while some tracked owner keeps the state alive, but the raw word itself owns nothing. Kira source cannot retain or release that word. If foreign code must keep state beyond a call, pass a `NativeState<T>` owner to an extern parameter declared with `retains:` and write `move owner`; that is the only Kira-to-C ownership transfer. C then owns exactly that reference and eventually balances it through the callback-state runtime ABI. Tokens are never reused: recovering a borrowed token after its final owner is gone traps instead of reading freed storage. Tokens belong to the runtime session that created them.

```kira
struct Counter { var hits: Int = 0 }

@FFI.Extern {
    library: host,
    symbol: host_keep_counter,
    abi: c,
    retains: userdata
}
function hostKeepCounter(userdata: RawPtr) -> Void

function handCounterToC() {
    let owner = nativeState(Counter {})
    hostKeepCounter(move owner)
    return
}
```

The `RawPtr` spelling in the extern describes C's ABI, not Kira ownership. The call-site argument remains a typed affine owner until the `move` transfers it. Calling `nativeUserDataRetain` or trying `nativeUserDataRelease(RawPtr(...))` is a compile-time error.

`nativeStateFree(owner)` is deprecated and reported by `KSEM360`. It consumes and releases one tracked owner; ordinary code lets the owner leave scope or uses `nativeUserDataRelease(owner)` explicitly.

Recovery gives an aliasing view of the stored state rather than a second owned value. Borrowing an owned state therefore requires storage rooted in a local, and an ordinary member read cannot copy a value that contains `NativeState`. Borrow that member in place, explicitly clone the tracked owner with `nativeUserData`, or move the containing owner instead.

This is not `@FFI.Struct { layout: c }`: that is a memory-layout contract visible to C, while callback state is opaque transport whose Kira layout native code never observes.

### What Foreign Code May Keep

Foreign code may retain Kira data only through an owned callback-state token, an owning callback handle whose captures live in callback state, or a `retains:` parameter's C storage with its paired release. It may not keep a borrowed Kira value, a stack place, a temporary string, an array element address, a writeback pointer, or a closure environment pointer past the call: none of those is owned by the callee, and a declaration that lets the callee keep something says so with `retains:`, which in turn requires the caller to `move` the argument.

## Deferred Shapes

Payload-carrying Kira enums as direct C values, direct `@FFI.Array` values in parameter or result positions, aggregate callback results, non-C ABIs, variadics, generic externs, and dynamic-only C libraries. Payload-less enums cross as C enum integers. Each deferred shape is refused with a typed diagnostic rather than mislowered.
