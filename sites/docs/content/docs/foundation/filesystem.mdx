`FileSystem.kira` reads and writes files on every backend.

| Operation | Works in |
| --- | --- |
| `readFile`, `writeFile` | text |
| `readFileRange`, `writeBytesFile` | bytes |
| `listDirectory` | a directory's entries |
| `fileExists`, `pathExists`, `isDirectory`, `fileSize` | questions about a path |
| `makeDirectory`, `renamePath`, `removePath` | changes to a path |

## Nothing Here Fails

A missing file, a parent directory that does not exist, a directory where a file was wanted: each answers `false`, `0`, or an empty array. A program has to be able to ask the outside world a question and hear no.

Two answers are worth knowing before relying on them:

- `removePath` is **recursive** on a directory.
- `readFile`'s `text` is the whole file, NUL bytes included, when the file is valid UTF-8; a file that is not is not text and reads as `""`. Binary data belongs in `readFileRange`.

## One Implementation, Three Backends

These sit on compiler intrinsics rather than on a bundled C library. The VM describes each operation and hands it to its host through `HostCapabilities`; native code calls `kira_rt_fs_*`. Both reach one implementation in `kira-runtime-abi`, which is what makes the backends agree byte for byte.

It is also why the portable VM core still builds for `wasm32-unknown-unknown`: a host that grants no filesystem simply refuses, and the web has no files to grant.
