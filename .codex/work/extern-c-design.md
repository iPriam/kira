# Consuming a Rust crate from Kira: the decision

This is the **Rust → Kira** direction: a Kira program calls into a Rust crate.
The opposite direction — a Kira library called *from* a Rust program — is
`.codex/work/kira-export-design.md`, and its § 12 states how the two relate.
The short test of which document you want: `#[kira::export]` on a Rust function
is here; `@Export` on a Kira function is there.

Decided 2026-07-18, superseding nothing: this builds on `.codex/work/ffi-design.md`
(seamlessness, host-performs-the-call, portable core untouched) and narrows it
where the code proved a cheaper path. Deviations from that note are called out
inline; everything else there stands.

## 1. The decision

**Build the uniform-adapter shape (agent 1's Shape B), reusing the trampoline
ABI that already exists in `kira-hybrid-runtime`.** A Rust crate opts in with a
`#[kira::export]` proc-macro from a new `kira-export` crate. The macro emits,
per exported function, a C-ABI adapter with the exact signature
`kira-hybrid-runtime/src/library.rs:34` already defines —
`unsafe extern "C" fn(args: *const BridgeValue, count: u32, out: *mut BridgeValue)`
— plus an embedded, versioned KFI1 metadata table. `kirac` drives `cargo build`,
reads KFI1, and machine-emits a `.kira` bindings file of oracle-syntax
`@FFI.Extern` / `@FFI.Pointer` / `@FFI.Callback` declarations (the oracle's own
autobinder pattern). The user imports the library and calls it like Kira code.
No libffi, no runtime signature construction, no `@Native` ceremony anywhere.

Composition of the other shapes:

- **Shape A's declaration surface is kept** — the generated bindings are written
  in the oracle-pinned `@FFI.*` syntax, and hand-writing those declarations
  against adapter symbols is legal. **Shape A's libffi call engine is not
  built**: a library that does not export the adapter ABI is refused by name, on
  every backend. Arbitrary C libraries (libc, sokol) are a later, separate
  decision.
- **Shape C (`.knl` prebuilt packages) is a later distribution phase** of this
  same runtime — same adapters, same KFI1, different producer. Not v1: local
  development of UI Foundation needs the cargo-driven path first regardless.
- **Shape D (crate-in-the-host) is rejected**: per-project host binaries break
  what `kira run` means and what a `.klbundle` is, and its claimed wasm
  advantage is false — `--backend vm --device wasm32` is refused today
  (`kira-cli/src/pipeline.rs`) and Shape D presupposes that work rather than
  removing it.

Why this shape wins: the hardest implementation problem (calling an arbitrary C
signature at runtime) is erased by construction — every export has one
signature, and the loader/marshaller for that signature is already written,
reviewed, and load-tested (`NativeLibrary::load/call/new_string/take_string`,
`library.rs:96-240`; free-contract in `marshal.rs:1-20`). The crate is the
single source of truth, so bindings cannot drift; a versioned marker symbol
makes a stale crate build fail the load or the link **by name**, the exact
lesson `RUNTIME_ABI_VERSION` encodes. And it directly serves the motivating
case: UI Foundation annotates its API once and becomes callable from Kira.

The trade accepted: only opt-in crates are callable in v1, and a consuming Kira
user needs a Rust toolchain until `.knl` lands (phase 3). Both are stated
refusals, not silent gaps.

## 2. What the user writes

The whole v1 user experience, for a library named `uifoundation`:

```kira
// package.kira — the existing manifest field, already documented as
// "Paths to NativeLibs/*.toml" (kira-manifest/src/project_manifest.rs:43-44)
let nativeLibraries = ["NativeLibs/uifoundation.toml"]
```

```kira
// app/main.kira — plain @Runtime code, no @Native, no @FFI, no ceremony
import uifoundation

@Main @Runtime
function main() {
    let w = uifoundation.windowCreate("hello", 800, 600)   // scalar + string + handle out
    uifoundation.windowShow(w)                             // handle in
    uifoundation.windowOnClick(w, onClick)                 // named-function callback
    uifoundation.windowDestroy(w)                          // explicit destructor
    return
}

function onClick(x: I32, y: I32) {
    print("click")
    return
}
```

On the Rust side:

```rust
#[kira::export]
pub fn window_create(title: &str, width: i32, height: i32) -> Handle<UifWindow> { .. }

#[kira::export]
pub fn window_on_click(window: Handle<UifWindow>, on_click: Callback<(i32, i32), ()>) { .. }
```

Behind the import, `kirac` emits `.kira-build/bindings/uifoundation.kira` —
machine-written, regenerated when the KFI1 hash changes, never committed:

```kira
// generated by kira FFI autobinding

@FFI.Pointer { target: UifWindow; ownership: borrowed; }
struct WindowHandle {}

@FFI.Callback { abi: c; params: [I32, I32]; result: Void; }
struct WindowClickCallback {}

@FFI.Extern { library: uifoundation; symbol: kira_x_uifoundation_window_create; abi: c; }
function windowCreate(title: CString, width: I32, height: I32): WindowHandle;

@FFI.Extern { library: uifoundation; symbol: kira_x_uifoundation_window_on_click; abi: c; }
function windowOnClick(window: WindowHandle, onClick: WindowClickCallback);
```

Coverage of the five required cases:

- **Scalar function** — works: `windowCreate(…, 800, 600)`; fixed-width scalars
  map directly (the language has I8..I64, U8..U64, F32/F64).
- **String** — works, params and results. `String → CString` at a param is the
  oracle-pinned transient copy: the callee never keeps it, the caller retains
  ownership. A returned Rust `String` becomes a Kira `String` the VM owns.
- **Array** — **REFUSED in v1.** An `[Element]` in an extern signature, or a
  `Vec<T>`/slice in a `#[kira::export]` signature, is a typed error
  (new code, § 6): the ownership question at the boundary — who frees the
  elements, what growth means for VM heap accounting — is exactly the hazard
  `bridge.rs:59-77` records, and it stays unanswered rather than guessed.
- **Opaque handle** — works: `@FFI.Pointer { target; ownership: borrowed }`
  (the only pinned ownership mode). A handle is a Copy word Kira never frees;
  the crate exports an explicit destructor.
- **Callback** — a **named top-level Kira function** works, crossing as a
  function id (never a machine pointer — Kira has no function pointer on any
  backend by deliberate closure design, `kira-semantics/src/closures/mod.rs`).
  An inline closure is **REFUSED** (oracle KSEM095, kept):

```kira
uifoundation.windowOnClick(w, { x, y in print("no") })
// error[KSEM095]: inline FFI callbacks are not supported
```

## 3. The four-backend matrix

**VM (`kira run`) — works.** A new appended opcode `CALL_FOREIGN` (0x45, after
`BIT_NOT` 0x44) carries a `foreign_id` indexing an appended KBC1
foreign-imports section (library, adapter symbol, signature). The interpreter
calls a new `HostCapabilities::call_foreign` default trait method (default:
`Err(ForeignCallError::NoForeignHost)`, mirroring `call_native`'s default), so
`kira-vm-runtime` stays wasm32-clean with nothing changed — the baseline
`cargo check -p kira-vm-runtime --target wasm32-unknown-unknown` was verified
green. The `kirac` host (`StdHost`, which today implements only `write_line`)
grows the implementation: dlopen the crate's cdylib, resolve adapter symbols by
the names KFI1 records (generalizing the `NativeLibrary` loader), verify the
ABI marker symbol at load, call the trampoline, marshal per the existing
`marshal.rs` discipline. No LLVM required — `kira run` against a Rust crate
works on the CI machine.

**LLVM/native (`kira build`) — works.** The backend declares each adapter
symbol (`LLVMAddFunction` is already routine for runtime symbols), emits the
`BridgeValue` array construction inline, and calls directly. The link step
widens `kira_llvm_backend::link::link()` — today exactly one object plus one
runtime archive — to accept extra staticlib inputs, and links the cargo-built
staticlib. Generated code references `kira_x_<lib>_abi_version_1`, so a stale
crate build fails the link by name. Adapter symbols that generated code does
not reference (string helpers, manifest, marker) are forced in by name from
KFI1, the same trick `HYBRID_HOST_SYMBOLS` documents.

**Hybrid — works.** The adapter staticlib links into the hybrid native half
(the same link widening), so the crate exists **once per process**: `@Native`
Kira code calls adapters directly; `@Runtime` Kira code takes the same
`CALL_FOREIGN → call_foreign` path as the pure VM, and the host resolves the
adapter symbols out of the loaded hybrid cdylib (the same dlsym-by-name pattern
it already uses for `kira_rt_str_*`). **This drops the `@Native` promotion
transform from v1 entirely** — a deviation from ffi-design.md, justified by
what the code showed: `--backend vm` and `--backend llvm` ignore
`@Runtime`/`@Native` (only hybrid splits), and on hybrid the host is in the
process either way, so routing beats rewriting execution modes. Two loaded
copies of the crate (host dlopens the standalone cdylib AND the native half
links it) would split the crate's own state — the single-copy rule exists to
prevent that.

**wasm — REFUSED BY NAME in v1**, at build time, before anything runs:

```
error[KCL...]: this program calls foreign function `uifoundation.windowCreate`,
and library `uifoundation` provides no wasm32 artifact: the wasm backend emits
one self-contained module and links no foreign code
```

The honest reasons: there is no wasm linker anywhere in the tree (the wasm
backend is a self-contained encoder, deliberately — "no external assembler, no
linker", `kira-wasm-runtime/src/lib.rs`), so a wasm32 build of the crate cannot
be merged into the module; and routing the adapter ABI through JS-supplied
imports needs a designed shim contract that does not exist. The module builder
does support imports (`kira.print`/`kira.trap` today), so the v2 yes-path is
real — extern-as-wasm-import with a shipped shim, or a module-merge step — and
is deferred as designed-later, not impossible. Programs that touch no foreign
function build for wasm exactly as today.

The ffi-design.md line "FFI on wasm comes from the `@Native` half via
promotion" described machinery that neither exists nor is needed (no hybrid
split reaches a wasm device; `pipeline.rs` refuses it by name) — superseded by
the above.

## 4. The seam contract: who owns and frees what

The seam's 3-mode `Ownership` enum (Owned/Borrow/BorrowMut) is untouched — it
describes the Kira/Kira hybrid seam. Foreign parameters have a **fixed**
contract per type; no per-parameter ownership byte crosses in KFI v1. At the
language level, an extern's parameters behave as `borrow` for strings and
`copy` for scalars and handles; `move` or `borrow mut` in an extern signature
is refused (nothing pins them, and a mutable borrow across the seam would
promise mutation of VM-owned storage that machine code cannot deliver).

| Type | Direction | Contract |
|---|---|---|
| Void, Bool, I8..I64, U8..U64, F32/F64 | both | copied by value; no ownership |
| String | Kira → Rust | oracle-pinned transient copy: host allocates a handle from the **library's** allocator (`kira_x_<lib>_str_new`), adapter decodes to `&str` valid for the call, adapter frees before returning; the Kira caller keeps ownership of its string |
| String | Rust → Kira | Rust returns `String`; adapter allocates a handle from the library allocator; host takes ownership — copy out, then free (`take_string` discipline, pinned in `marshal.rs`) |
| Handle (`@FFI.Pointer`, tag HANDLE=8) | both | a Copy word, payload = pointer bits; Kira never frees or dereferences it; lifetime is the crate's, ended only by an explicit exported destructor; null is a legal value (it is a word, and Kira cannot dereference it anyway) |
| Callback (tag CALLBACK=9) | Kira → Rust | payload = function id; the crate holds the id and calls back through an installed invoker; nothing to free |
| struct / enum / array | both | **REFUSED** — the existing three-site refusal stands (`bridge.rs` tags never travel, backend refuses the crossing, manifest describes-not-carries); Rust-side `Vec`, slices, structs, `Option`, `Result` are refused at bind time naming the function and type |

Why the library-allocator handle discipline and not caller-owned buffers: it is
the discipline the hybrid seam already pins, one set of rules for every
crossing in the workspace, and it is what makes the cross-allocator hazard
(`library.rs:1-15` header) structurally impossible — bytes allocated by a
library are freed only by that library's own exported free.

**Callbacks in detail.** v1 callbacks are named top-level functions, exact
signature match (KSEM045 kept, KSEM043 kept, KSEM095 kept). The oracle's
KSEM044 (`@Runtime` callback targets refused) is **deliberately not ported** —
the recorded seamless requirement makes it wrong here, and re-entry machinery
exists: `Program::run`/`Program::call` take `&self` (re-entrancy is built and
tested), and the hybrid session already installs a C-ABI invoker
(`kira_hybrid_call_runtime` precedent). On VM/hybrid the host installs an
invoker that re-enters the interpreter by function id; on LLVM the generated
binary installs a generated dispatcher (a switch over callback ids — the same
defunctionalization pattern the closure design chose, deliberately not a
function pointer table). Callbacks may be invoked **only on the program's
thread** in v1 — the existing session rule (`session.rs`: fatal on a foreign
thread) is the contract, stated in `kira-export`'s docs. Callback state cannot
live in captures (captures are scalar-only by KSEM117 and a named function has
none); state lives on the Rust side behind handles, which is how a widget-tree
library is shaped anyway. The oracle's `nativeState` family is not in v1.

## 5. How a Rust crate is built and linked

1. **Manifest.** `package.kira`'s existing `native_libraries` field lists
   `NativeLibs/<name>.toml` paths. The TOML schema fills the empty
   `kira-native-lib-definition` crate (layer 3, "Design pending" by intent):
   library name (must be a valid Kira identifier), `kind = "rust-crate"`, crate
   path, and later optional per-target prebuilt artifacts.
2. **Build.** `kirac` runs `cargo build --release -p <crate>` in the crate's
   directory. The crate depends on `kira-export` (new workspace crate, shipped
   for crate authors, depends on `kira-runtime-abi` so `BridgeValue`'s layout
   is defined exactly once) and declares `crate-type = ["cdylib", "staticlib"]`
   — cdylib for the VM path, staticlib for LLVM/hybrid linking
   (`kira-native-bridge/Cargo.toml` is the two-crate-type precedent).
3. **Symbols.** Every exported symbol is prefixed with the crate name so two
   libraries can link into one binary without collision:
   `kira_x_<lib>_<fn>` (adapters), `kira_x_<lib>_str_new/free/data/len` (the
   library's string allocator — deliberately **not** named `kira_rt_str_*`,
   which would collide with the Kira runtime's own at static link),
   `kira_x_<lib>_manifest` (returns KFI1 bytes), `kira_x_<lib>_abi_version_1`
   (the guard marker), `kira_x_<lib>_install_invoker` (callback re-entry).
   The manifest and marker names are the only ones constructed by pattern;
   everything else is read out of KFI1.
4. **Metadata.** KFI1 is a new append-only wire format (magic `KFI1`,
   hand-encoded like KBC1, decoder validates every byte, round-trip and
   truncation tests in the same change): contract version, library name, and
   per export the Rust name, the Kira name (deterministic snake_case →
   camelCase; a collision after mapping is a bind-time refusal), the adapter
   symbol, param/result types, handle target names (namespaced per library),
   and callback shapes. `kirac` obtains it by dlopening the host-target cdylib
   and calling `kira_x_<lib>_manifest` — no weaker trust than already running
   the crate's `build.rs` via cargo.
5. **Bindings.** Emitted to `.kira-build/bindings/<lib>.kira`, deterministic
   order, regenerated when the hash of the KFI1 bytes changes, and joined to
   the program graph as module `<lib>` (an existing user module of the same
   name is a typed collision error).
6. **Per backend.** VM: host dlopens the cdylib at run, verifies
   `kira_x_<lib>_abi_version_1` at load. LLVM: staticlib added to the widened
   link line; marker referenced by generated code. Hybrid: staticlib linked
   into the native half; host resolves adapter symbols from the loaded hybrid
   library. wasm: refused (§ 3).

## 6. Oracle-pinned versus new design

**Oracle-pinned, followed as-is** (evidence in `.codex/tmp/specs/annotations-ffi.md`):
the `@FFI.Extern { library; symbol; abi: c; }` bodyless-`;` declaration shape
and its whole diagnostic set (KSEM035/036/039/041); annotation-block grammar
(`:` binder, optional `;`); `@FFI.Pointer { target; ownership: borrowed }` and
`@FFI.Callback { abi; params; result }` declaration forms (KSEM037/038/040);
`RawPtr`/`CString`/`CBool` and the coercion table; the transient-copy string
rule (pinned by a 300-iteration leak test); callbacks as named function refs
with exact signatures (KSEM043/045/095); machine-emitted `.kira` bindings as a
pattern; seamless extern calls from ordinary code **on the VM** (corpus
`ffi-dynamic` runs on `[.Vm]` with plain `@Runtime` callers).

**Deliberate deviations from the oracle** — owned here, never presented as
pinned:

- **KSEM093 is not ported.** The oracle refuses direct extern use outside
  `@Native` on llvm/hybrid; this repo's recorded standing requirement (memory +
  ffi-design.md) is seamlessness on every backend. The oracle's fail-corpus
  test for KSEM093 is deliberately not ported; a pass test proving the same
  program runs on all backends replaces it.
- **KSEM044 is not ported.** Named `@Runtime` functions are legal callback
  targets, via the invoker (§ 4).
- **Stricter than the oracle:** unknown fields in FFI blocks are rejected (the
  oracle silently ignores them; its own spec §14 says the port should reject);
  `ownership: owned|opaque` are refused (they parse in the oracle but have no
  call site); `@FFI.Alias` is refused (machine-emitted only, no call site,
  no test pins its behavior).

**Entirely new Kira design, beyond the oracle:** everything crate-shaped — the
`#[kira::export]` macro, the adapter ABI as a *foreign-library* contract (the
signature is reused from this repo's own hybrid seam), KFI1, the autobinder
reading a Rust crate, the `NativeLibs/*.toml` schema, `call_foreign`, the
`CALL_FOREIGN` opcode, the HANDLE and CALLBACK tags, the per-library symbol
scheme and ABI marker, cargo driving, and every wasm answer. The oracle binds C
symbols someone else built; "consume a Rust crate as if it were a Kira
library" is this repo's own goal and this document is its specification.

## 7. Wire-format impact

All additions, no bumps. `RUNTIME_ABI_VERSION` stays 2 — no existing
`kira_rt_*` signature changes.

- **Opcode:** `CALL_FOREIGN = 0x45`, appended after `BIT_NOT = 0x44`.
- **KBC1:** an appended foreign-imports section (per entry: library name,
  adapter symbol, param tags, result tag), indexed by `CALL_FOREIGN`'s
  operand. Round-trip and truncation tests extended in the same change.
- **KHM1:** an appended field recording the foreign libraries linked into the
  native half (name + symbol list), so the host knows to resolve adapters from
  the hybrid library. Same test discipline.
- **BridgeValueTag:** `HANDLE = 8` **has landed** — the export direction's step 2
  defined it in `kira-runtime-abi/src/bridge.rs`, with `BridgeData::Handle`, a
  decode arm, and pinned tag-byte tests. One tag serves both directions, as
  § 12 of `kira-export-design.md` says, so this direction consumes it rather
  than appending its own; the payload is pointer bits here and a rooted-heap id
  there, which is exactly the "opaque to the receiver" contract the tag's doc
  states. `CALLBACK = 9` is still unassigned and belongs to this direction
  alone. STRUCT/ARRAY/ENUM continue to never travel.
- **NativeArg/NativeResult:** `Handle(u64)` **has landed** with the tag; only
  `Callback(u32)` on the arg side remains for this direction. Safe Rust enums,
  no wire implication, no bump (agent 2's correction: the VM path speaks these,
  not BridgeValue).
- **HostCapabilities:** new `call_foreign` default method + `ForeignCallError`
  — a trait addition with a refusing default; the portable core links nothing
  new.
- **New symbol family, new guard:** the `kira_x_<lib>_*` contract is versioned
  by its **own** marker (`kira_x_<lib>_abi_version_1`), mirroring the
  `RUNTIME_ABI_VERSION` name-is-the-guard pattern. A breaking change to the
  adapter contract renames the marker to `..._version_2`; `kira-export` owns
  that constant and its pinning test.
- **`kira_rt_*`:** no additions and no changes in v1 (the hybrid routing needs
  none — resolution-from-the-hybrid-library replaced the earlier
  invoker-helper idea).

## 8. Implementation plan

Ordered; each step lands green on all four backends (a backend refusing by
typed error is green). The style is the migration's: surface first, checked but
refused; then one backend at a time behind the same surface.

1. **Manifest + library definition** — fill `kira-native-lib-definition`
   (TOML schema, per-target resolution model) and wire
   `kira-manifest`/`kira-project` resolution. Cheap, frontend/toolchain only.
2. **`kira-export` + fixture** — new `kira-export` and `kira-export-macros`
   crates (adapters, KFI1 emission, string allocator, marker, invoker install)
   plus a workspace fixture crate with `crate-type = ["cdylib"]` that
   `cargo build --workspace` drops into the profile dir. This is what makes the
   feature CI-provable without LLVM — note the entire
   `backend_parity` suite is `#![cfg(feature = "llvm")]` and never runs on CI,
   so the VM-path tests go in a separate non-LLVM CLI test.
3. **Frontend surface** — parse and check `@FFI.Extern`/`@FFI.Pointer`/
   `@FFI.Callback` with every pinned diagnostic, plus the new refusals (arrays/
   structs/enums in extern signatures, `move`/`borrow mut` params, owned/opaque,
   `@FFI.Alias`, unknown block fields). Calls compile-check but are refused
   with a typed "foreign calls are not lowered yet" on every backend. Cheap,
   layers 1–2.
4. **Autobinder** — KFI1 decoder, cargo driver, binding emission, staleness
   hash, module-graph join. Toolchain layers; calls still refused.
5. **The VM path** — HANDLE/CALLBACK tags, NativeArg/NativeResult arms,
   `call_foreign`, `CALL_FOREIGN` opcode + KBC1 section, interpreter arm,
   generalized foreign loader, `StdHost` implementation, load-time marker
   check, and the build-time wasm refusal. `kira run` works end to end against
   the fixture crate; proven on CI. Touches every layer 0–4 plus the CLI.
6. **The LLVM path** — declare adapters, inline marshalling codegen, widen
   `link.rs` for extra staticlibs, marker reference, symbol force-in.
   LLVM-gated parity tests.
7. **The hybrid path** — link the staticlib into the native half, host
   resolution of adapters from the hybrid library, KHM1 field. Parity tests.
8. **Callbacks** — CALLBACK crossing, host invoker on VM/hybrid (reusing the
   session machinery), generated dispatcher on LLVM, single-thread fatal
   coverage, KSEM044-deviation pass test.
9. **Docs and examples** — refresh `kira-doc` surface docs, add a worked
   example package, and update ffi-design.md's superseded wasm paragraph to
   point here.

Phase 2 (after v1, in order of pull): `@FFI.Struct` with the oracle's pinned
C-layout/zero-fill rules and RawPtr coercion; `.knl` prebuilt packages so
consumers need no Rust toolchain; the wasm yes-path design. Phase 2 items are
recorded so nobody re-derives them, and none blocks v1.

## 9. What v1 deliberately does not do

- **Call non-adapter (arbitrary C) libraries** — no libffi in the frozen
  workspace deps, no unsafe runtime signature construction; refused by name on
  every backend, uniformly, so parity holds by refusal. Revisit only as its
  own decision.
- **Foreign calls on wasm** — refused by name at build time (§ 3); no wasm
  linker exists and a JS shim contract is undesigned. The import-section
  yes-path is real and deferred, not denied.
- **Arrays, structs, and enums across the seam** — the existing never-travels
  refusal stands; the array ownership hazard is documented in `bridge.rs` and
  stays unanswered rather than guessed. Rust-side aggregate types are refused
  at bind time.
- **`@FFI.Struct` / `@FFI.Array`** — deferred whole to phase 2 with their
  oracle-pinned rules recorded; v1 refuses the annotations with a typed
  "not supported yet" so no partial surface ships.
- **`@FFI.Alias`** — refused; no call site anywhere in the oracle, machine
  emission is its only producer, and refusing beats guessing (the
  `print(struct)` precedent).
- **Closure callbacks** — refused (KSEM095): no function pointer exists on any
  backend by the closure design's own charter, and captures are scalar-only
  (KSEM117). Named functions plus Rust-side state cover the UI case.
- **Off-thread callbacks** — the existing v0 single-thread session rule holds;
  a crate invoking a callback from another thread hits the existing fatal.
- **`owned`/`opaque` handle ownership, `move`/`borrow mut` extern params,
  unknown FFI block fields** — refused, each for lack of any pinned behavior.
- **The `nativeState` family** — hybrid-only in the oracle and unneeded by the
  adapter model; deferred until something pulls it.
- **Prebuilt distribution** — v1 consumers run cargo; `.knl` is phase 2/3.

## 10. Open questions

- **Diagnostic numbers.** The new refusal codes need numbers from this repo's
  registry (KSEM runs to 157 here; oracle codes are mirrored where adopted).
  Assign the next free block at implementation — the titles above are the
  spec, the numbers are bookkeeping.
- **Build profile for `kira run`.** `--release` adapters by default, or follow
  a kirac profile flag? Affects iteration speed on UI Foundation itself.
- **KFI staleness vs cargo fingerprinting.** Binding regeneration keys off the
  KFI1 hash; whether kirac should also short-circuit the cargo invocation when
  nothing changed, or always let cargo decide, is an ergonomics call.
- **Callback re-entrancy depth.** The interpreter re-enters safely, but a
  callback that calls back into the same library that is mid-call is a
  crate-side reentrancy question; v1 documents "the crate must tolerate its
  own reentrancy or not recurse", and whether Kira should enforce anything is
  open.
- **Handle type identity across libraries.** Targets are namespaced per
  library; whether two libraries can ever share a handle type (a windowing
  crate handing a handle to a render crate) is deferred until a real case
  exists.
- **Hand-written `@FFI.Extern` against adapter symbols** — legal by
  construction; whether to document it as supported surface or leave it as an
  implementation detail of the autobinder.
- **The wasm yes-path shape** — module merge (needs a linker or an object
  merger in-tree) versus JS-shim imports (needs a shim wire contract). Decide
  when wasm UI is actually pulled; both are compatible with this design's
  surface.
