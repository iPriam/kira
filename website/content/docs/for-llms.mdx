## What Kira is, in one paragraph

Kira is a readable, ownership-aware systems-and-apps language compiled from a Zig monorepo. It is **dual-mode**: the same program runs on a bytecode **VM** (`kira run`), an **LLVM/native** backend (`kira build`), a **hybrid** runtime that mixes bytecode and native code, and a **WASM** target (`kira build --target wasm32-emscripten`). Kira UI is expressed through a **construct family** surface (a SwiftUI-style declaration model) and shaders through a dedicated `.ksl` language.

## The single most important rule

**Backend parity is a hard requirement, not a nicety.** A feature is only "done" when it works across VM and LLVM/native (and hybrid/WASM where relevant), *or* is explicitly rejected with a tested diagnostic. When you reason about a feature, never assume "VM works, so it works." Check the [Execution and Feature Status](/docs/language-reference/execution-and-feature-status) matrix, which marks exactly which backends run each surface.

Corollary for generated code: do not invent syntax. If a form is not in the [Language Reference](/docs/language-reference), it probably is not accepted yet.

## What actually executes today

Across VM, LLVM, and hybrid: functions; integers/floats/strings/booleans; `let`/`var`; arithmetic, comparison, and short-circuit operators; `if`/`for`/`while`/`switch`/`match`; arrays; enums + exhaustive `match`; named structs + methods; `@Printable` print dispatch; class inheritance dispatch; callbacks and captures; `attempt`/`try`/`handle` over `Result`; and a growing slice of the construct surface — the `node` bridge, `any Family` coercion, and `@Content` widget trees.

FFI differs by backend: the **VM runs direct FFI through LibFFI** (no `@Native` needed), while **LLVM/native and hybrid require `@Native`** at the declaration that touches the symbol (diagnostic `KSEM093`).

## Conventions when writing Kira

- Construct declarations are headed by the family name: `Widget Button { ... }` — not `class Button: Widget`.
- Construct families inherit with `extends`, not `:`. `extend C { ... }` adds fluent modifiers; the two are different.
- Property values are supplied by a `properties { ... }` **section**, not a constructor call.
- Error handling is `attempt { ... try expr ... } handle { Variant { ... } }` — the keyword is `try`, not `?`.
- Ownership: Kira owns by default; `borrow` / `borrow mut` / `move` are explicit. Non-trivial `copy` and returned borrows are reserved and currently diagnosed, not silently accepted.
- This manual is **current-status-first**: it describes the implementation in the repository today, marks partial behavior as partial, and omits unsupported topics rather than padding them. Match that honesty.
